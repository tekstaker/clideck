<objective>
Build the observable, hard-timed shutdown sequence: an ack banner, per-step
labels with timing, a 3s heartbeat, and a 10s watchdog — and unit-test the
load-bearing behaviours (isolated-try regression, watchdog-armed).

Because `server.js` binds a port on require and has no `module.exports`, the
orchestration is extracted into a new `shutdown.js` module exposing a
`createShutdown({ plugins, activity, sessions, getConfig, log, exit, timeoutMs })`
factory. Dependencies are injected so the full D-08 sequence is unit-testable
WITHOUT booting a real server. `server.js` requires the factory, wires it with
the real modules, and registers it on SIGINT/SIGTERM (passing the signal name).

Purpose: D-02 (step helper), D-04 (heartbeat), D-05 (watchdog), D-06 (clear
heartbeat on happy path), D-07 (garbled-output mitigation, implementer's choice),
D-08 (exact order of operations), D-09 (Vitest coverage).
Output: new `shutdown.js`; modified `server.js`; new `tests/shutdown.test.js`;
patched `package.json` version.

    write `[clideck] ${label}… ` (NO trailing newline), then in a try/catch
    `await fn()`; on success write `done (${Date.now()-t0}ms)\n`, on throw write
    `failed: ${e.message}\n` and SWALLOW the error (do NOT rethrow — the isolated
    try shape: one step failing must never abort later steps or the exit, AC 3 /
    D-01). `await fn()` tolerates fn being sync or returning a Promise.

    `onShutdown(signal)` (D-08, exact order):
      1. Banner: if signal === 'SIGTERM' write
         `\n[clideck] SIGTERM received — shutting down…\n`, else
         `\n[clideck] Ctrl+C received — shutting down…\n`. The leading `\n` is
         load-bearing (separates from the shell's `^C`; CONTEXT "Specific Ideas").
         This is the FIRST statement (AC 1, ≤50ms — nothing async precedes it).
      2. Arm watchdog: `const wd = setTimeout(() => { log('[clideck] shutdown took
         too long — forcing exit'); exit(0); }, timeoutMs)` (D-05, AC 5).
      3. Arm heartbeat: `const hb = setInterval(() => { ... }, heartbeatMs)` whose
         body logs `[clideck] still shutting down… (current step: ${currentStep},
         elapsed: ${Math.round((Date.now()-start)/1000)}s)` where `start` is captured
         at onShutdown entry (D-04, AC 4). First tick at +heartbeatMs.
      4. `await step('flushing plugins', () => plugins.shutdown())`.
      5. `await step('stopping activity', () => activity.stop())`.
      6. `await step('persisting sessions', () => sessions.shutdown(getConfig()))`.
      7. `clearInterval(hb)` then `clearTimeout(wd)` (D-06, D-05 happy-path clear).
      8. `log('[clideck] goodbye.')` (AC 6).
      9. `exit(0)`.

    D-07 garbled-output mitigation (implementer's choice — pick ONE and note it
    in the SUMMARY): the chosen-and-recommended option is the `stepInProgress`
    flag — set true around the `write(label…)` → `write(done…)` span; when the
    heartbeat fires, if `stepInProgress` it prefixes its line with a leading `\n`
    so it breaks cleanly off the dangling label, otherwise prints normally. (The
    alternatives — always-leading-`\n` on heartbeat, or label-on-its-own-line —
    are acceptable; document whichever you ship.)

    Do NOT hard-code anything that should be injected (timeoutMs, heartbeatMs,
    exit, log, write are all deps with the D-05/D-04 defaults). The watchdog cap
    stays a hard-coded DEFAULT of 10000ms (env-config is deferred per D-05).
