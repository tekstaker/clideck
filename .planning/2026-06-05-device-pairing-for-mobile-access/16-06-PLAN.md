## RESEARCH §7 quoted recommendation (verbatim — this is the canonical client-side auth-fail shape)
From RESEARCH §7:
> Use Option 7A as the primary mechanism (reject in `verifyClient` → HTTP 401 → client sees 1006).
> Soften the false-positive case by **distinguishing the boot-time WS handshake from the in-flight revoke case**:
>   - **Boot-time auth failure** (`event.code === 1006` AND we have a `localStorage.deviceToken`): clear and redirect to /pair. Lance might re-OTP unnecessarily on a transient network blip; we accept this rare false-positive.
>   - **In-flight revoke** (`event.code === 4401` because the connection was already up when revoke ran and Pattern A from R-4 called `ws.close(4401, 'revoked')`): clear and redirect to /pair. This path is unambiguous.

The hybrid shape MUST appear in app.js literally as the conditional `event.code === 4401 || (!connectedAtLeastOnce && event.code === 1006 && hasToken)`. Wave 0 e2e/revoke-flow.spec.js (and the 16-08 verification) checks this branch on the self-revoke path.

## creator.js as a fetch+ POST analog (PATTERNS §1 row 12)
There is no perfect analog for the standalone pair page; pair.js stands on its own. The closest
existing fetch-based POST is in the creator pre-flight, but it goes through the WS `send()` path
not fetch. Phase 16's pair.js uses fetch because the WS isn't open yet pre-pair (chicken-and-egg).

## /pair/redeem response shape (16-04 RESEARCH §10.4)
On success: `{ ok: true, device_id: 'dev_...', token: '<43-char base64url>', label: '<normalised>' }`
On failure: `{ ok: false, error: 'expired' | 'used' | 'invalid' | 'invalid-json' }`
Status codes: 200 / 410 (expired) / 400 (others).

pair.js MUST persist BOTH `clideck.deviceToken` AND `clideck.deviceId` so app.js boot can populate
`state.deviceId` for the Settings panel to identify "This device" (16-07).
